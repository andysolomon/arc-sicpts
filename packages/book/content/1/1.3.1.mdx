<Prose>

Functions are abstractions that describe compound operations on numbers independent of the particular numbers. `cube` describes how to cube any number, not just 3. A language that could only name numbers would make us express every pattern at the level of the primitives. Often the same pattern is used with several different functions, and to name it we need functions that accept functions as arguments or return them as values. These are *higher-order functions*, and they are the subject of §1.3.

Here are three functions. The first sums the integers from `a` to `b`, the second sums their cubes, and the third sums a sequence of terms that converges, very slowly, to π / 8.

```js
function sum_integers(a, b) {
  return a > b ? 0 : a + sum_integers(a + 1, b);
}

function sum_cubes(a, b) {
  return a > b ? 0 : cube(a) + sum_cubes(a + 1, b);
}

function pi_sum(a, b) {
  return a > b ? 0 : 1 / (a * (a + 2)) + pi_sum(a + 4, b);
}
```

They share a common pattern and differ only in the name, the function of `a` used to compute each term, and the function that gives the next value of `a`. Mathematicians long ago named the pattern *summation*, written with a sigma, and the power of the notation is that it lets one talk about the concept of summation itself rather than particular sums. We can do the same by turning the slots into parameters.

</Prose>

<Example index={0} file="sum.sicp" source={sumProgram} anim="process">

The substitution model, extended to functions as arguments. A function's name is a value like any other: `sum(cube, 1, inc, 3)` passes `cube` and `inc` along unevaluated, and `term(a)` becomes `cube(1)` when `cube` is substituted for `term`. The pending additions pile up just as factorial's multiplications did.

</Example>

<Prose>

With `sum` in hand, each summation is one line, and new ones are as easy. `pi_sum` needs a term function and a next function of its own, so it declares them inside its body as in §1.1.8. Its value converges on π / 8, so the program multiplies by 8.

</Prose>

<Example index={1} file="pi_sum.sicp" source={piSumProgram}>

250 terms give π to two decimal places. The series converges slowly: each additional digit costs about ten times as many terms. Section 3.5.3 accelerates exactly this series.

</Example>

<Prose>

Once we have `sum`, we can use it as a building block for further concepts. The definite integral of a function *f* between the limits *a* and *b* can be approximated numerically by the *midpoint rule*: add up the values of *f* at the middle of strips of width *dx*, and multiply by *dx*. The function `integral` says exactly that, handing `sum` the very function it was given.

</Prose>

<Example index={2} file="integral.sicp" source={integralProgram} anim="integral">

Each value of `cube` that the program computed becomes a rectangle under the curve, at the point where the trace says it was evaluated. With *dx* = 0.05 there are 20 rectangles and the sum is 0.2496875. The exact value is 1/4. Try 0.01, which draws a hundred. Much smaller than that and the trace fills up before the program finishes, so only the first rectangles are drawn.

</Example>

<Exercise id="1.29">

*Simpson's rule* is a more accurate method of numerical integration. The integral of *f* between *a* and *b* is approximated as (*h* / 3)(*y*₀ + 4*y*₁ + 2*y*₂ + 4*y*₃ + 2*y*₄ + ⋯ + 2*y*ₙ₋₂ + 4*y*ₙ₋₁ + *y*ₙ), where *h* = (*b* − *a*) / *n* for some even *n*, and *y*ₖ = *f*(*a* + *kh*). Declare `simpson(f, a, b, n)` using `sum`, and compare its results for `cube` between 0 and 1 with those of `integral`.

<Solution>

**Solution.** Sum over *k* from 0 to *n* with a term that multiplies *y*ₖ by its coefficient: 1 at both ends, 4 for odd *k*, 2 for even *k*. Simpson's rule is exact for polynomials up to degree three, so for `cube` it gives 0.25 with any even *n*, up to rounding, where the midpoint rule needed *dx* = 0.01 to get within 0.0001.

</Solution>
</Exercise>

The `sum` function above generates a linear recursion. It can be rewritten so that the sum is performed iteratively. Show how to do this by filling in the missing expressions.

<Solution>

**Solution.** `iter` returns the accumulated `result` once `a` passes `b`, and otherwise calls itself with `next(a)` and `result + term(a)`. Nothing is left pending, and the checker measures an iterative process.

<Exercise id="1.31">

The `sum` function is only the simplest of a vast number of similar abstractions. Write an analogous function called `product` that returns the product of the values of a function at points over a given range, by means of a recursive process, and `product_iter` that does the same by means of an iterative process. Show how to define `factorial` in terms of `product`. Also use `product` to compute approximations to π using John Wallis's formula π / 4 = (2 · 4 · 4 · 6 · 6 · 8 ⋯) / (3 · 3 · 5 · 5 · 7 · 7 ⋯).

<Solution>

**Solution.** `product` is `sum` with `*` for `+` and 1 for 0. `factorial(n)` is `product(identity, 1, inc, n)`. Grouping Wallis's factors in pairs gives a term (2*k*)(2*k* + 2) / (2*k* + 1)² for each *k*; a thousand of them give π to within 0.001.

</Solution>
</Exercise>
<Exercise id="1.32">

Show that `sum` and `product` are both special cases of a still more general notion called `accumulate`, which combines a collection of terms using some general accumulation function: `accumulate(combiner, null_value, term, a, next, b)`. `combiner` is a function of two arguments that says how the current term is combined with the accumulation of the preceding terms, and `null_value` says what to use when the terms run out.

<Solution>

**Solution.** `accumulate` is `sum` with the `+` and the 0 turned into parameters. Then `sum` is `accumulate(plus, 0, …)` and `product` is `accumulate(times, 1, …)`. Section 2.2.3 meets `accumulate` again as one of the conventional interfaces for sequences.

</Solution>
</Exercise>
