<Prose>

In using `sum` as in §1.3.1, it seems terribly awkward to declare trivial functions such as `pi_term` and `pi_next` just so we can use them as arguments. It is more convenient to say directly "the function that returns its input incremented by 4". Every function so far has been written as parameters, an arrow and a body, and then named with `const`. The part to the right of the `=`, a *lambda expression*, is complete without the name. On its own it says exactly what we want:

```js
x => x + 4
```

and "the function that returns the reciprocal of its input times its input plus 2" is

```js
x => 1 / (x * (x + 2))
```

A lambda expression's value is a function, and it can be written wherever that function is used. With a single unannotated parameter, the parentheses around it can be left out. Then `pi_sum` needs no helpers at all:

```js
const pi_sum = (a: number, b: number): number =>
  sum(x => 1 / (x * (x + 2)), a, x => x + 4, b);
```

The two lambda expressions carry no annotations, and need none: the annotations of `sum` already say that `term` and `next` take a number and return one. A named function is different, because its annotations are what its users read, so every named function in this book has them.

So a named function such as `const plus4 = (x: number): number => x + 4;` is just a constant declaration whose right-hand side is a lambda expression. JavaScript also has an older form that does the same job, the *function declaration* `function plus4(x) { return x + 4; }`. The language still accepts it, and you will meet it in other programs; this book names its functions with `const` instead. And like any expression that has a function as its value, a lambda expression can be applied directly, without ever being named.

</Prose>

<Prose>

Another use of lambda expressions, and of declarations inside a body, is to give names to intermediate values. Suppose we wish to compute *f*(*x*, *y*) = *x*(1 + *xy*)² + *y*(1 − *y*) + (1 + *xy*)(1 − *y*). It is clearer to name *a* = 1 + *xy* and *b* = 1 − *y* and write *f* = *xa*² + *yb* + *ab*. Constant declarations inside the function body do this, and the names `a` and `b` are local to the body, just as parameters are local to a function.

</Prose>

<Example index={1} file="local_names.sicp" source={localNamesProgram} anim="frames">

Applying `f` makes a frame for `x` and `y`. Because the body declares names of its own, the evaluator also makes a frame for the body, inside the first, where `a` and `b` are bound. Their initialisers can use `x` and `y`, found one frame out.

</Example>

<Prose>

Sometimes a function has to choose between two sequences of steps rather than two values. The *conditional statement* chooses between two blocks of statements. Its predicate is in parentheses after `if`, and each branch is a block in braces, which may declare its own constants:

</Prose>

<Example index={2} file="expmod_if.sicp" source={conditionalStatementProgram} anim="calls">

The `expmod` of §1.2.6, written with a conditional statement. In the even case, a constant names the half power, which is then squared, so each level of the call tree makes a single recursive call rather than two.

</Example>

<Prose>

A conditional statement's branches are statements, so a function that uses one needs a block for its body, and each branch needs its own `return`. A conditional expression has expressions for branches and is itself an expression, which is why it can be a function's whole body, passed as an argument, or nested; both forms only ever evaluate one of their branches.

</Prose>

<Exercise id="1.34">

Suppose we declare the function `f` below. Then `f(square)` is 4, and `f(z => z * (z + 1))` is 6. What happens if we (perversely) ask the interpreter to evaluate the application `f(f)`? Work it out with the substitution model before running it. Record the value that the evaluator finally tries to use as a function, and the argument it tries to give it.

<Solution>

**Solution.** `f(f)` substitutes `f` for `g` in `g(2)`, giving `f(2)`. That substitutes 2 for `g`, giving `2(2)`. The number 2 is not a function, so the evaluator stops with "Cannot apply 2: it is not a function". The annotation on `g` already said as much, since `f` does not take a number, but annotations are not checked, so the mistake surfaces only when `2(2)` is reached.

</Solution>
