<Prose>

Pairs are the glue from which compound data is made. The standard way to picture a pair is *box-and-pointer notation*: each compound object is a pointer to a box, and the box for a pair has two parts, the left holding the head and the right holding the tail.

Since §2.1 we have known that `pair` can combine pairs as well as numbers. That makes pairs a universal building block: the four numbers 1, 2, 3 and 4 can be glued together in many ways, two of which are drawn below. The ability to make pairs whose elements are pairs is called the *closure property* of `pair`. In general, an operation for combining data objects satisfies the closure property if the results of combining things with it can themselves be combined with it. Closure is the key to power in any means of combination, because it lets us build *hierarchical* structures: structures made of parts, which are made of parts, and so on.

Chapter 1 relied on closure from the start, since the elements of a combination can themselves be combinations. Section 2.2 takes up its consequences for compound data. (The word comes from algebra, where a set is closed under an operation when the operation keeps you inside the set. It has nothing to do with the closures of chapter 1, the functions that remember their frames.)

</Prose>

<Example index={0} file="closure.sicp" source={closurePropertyProgram} anim="pairs">

One box per pair, a pointer wherever a pair holds another pair. `pairs_of_pairs` and `another_way` hold the same four numbers in different shapes, and the program's value glues the two structures into a third: a pair of pairs of pairs.

</Example>

<Prose>

One of the useful structures we can build with pairs is a *sequence*, an ordered collection of data objects. The most straightforward representation is a chain of pairs: the head of each pair is an item of the sequence and the tail is the next pair in the chain. The tail of the final pair is `null`, drawn as a diagonal slash, which marks the end. The sequence 1, 2, 3, 4 is

```js
pair(1, pair(2, pair(3, pair(4, null))));
```

A sequence of pairs formed by nested `pair` applications is a *list*, and the primitive `list` builds one: `list(1, 2, 3, 4)` is the sequence above. In general `list(a₁, a₂, …, aₙ)` is `pair(a₁, pair(a₂, pair(…, pair(aₙ, null)…)))`.

The interpreter prints pairs in *box notation*, a textual box-and-pointer diagram: `pair(1, 2)` prints as `[1, 2]`, and the list above as `[1, [2, [3, [4, null]]]]`. Box notation is hard to read once lists nest, so when we want to show the list nature of a structure we use *list notation* instead, the application of `list` that would build it: `list(1, 2, 3, 4)`. The primitive `display_list` prints in list notation.

`head` selects the first item of a list, and `tail` the sublist of all but the first. Nested applications of the two extract the second, third and later items. `pair` makes a list like the original but with an extra item at the front. The value `null`, which ends every chain, can be thought of as a sequence of no elements: the *empty list*.

</Prose>

<Example index={1} file="one_through_four.sicp" source={oneThroughFourProgram} anim="pairs">

`display` prints box notation and `display_list` list notation. `ten_through_four` is one new pair whose tail is `one_through_four` itself: `pair` does not copy the list it extends. The last line checks, with `equal` from the list library, that `list` built exactly the nested pairs of the text.

</Example>

<Prose>

**List operations.** Lists come with conventional techniques for manipulating them by walking down them with `tail`. The function `list_ref` takes a list and a number *n* and returns the *n*th item, counting from 0. For *n* = 0 it returns the head of the list; otherwise it returns the (*n* − 1)st item of the tail.

Often we walk down a whole list. The primitive predicate `is_null` tests whether its argument is the empty list, and `length` shows the typical pattern: the length of any list is 1 plus the length of its tail, applied until we reach the base case, where the length of the empty list is 0. Like `factorial`, `length` can also be written to generate an iterative process:

```js
function length(items) {
  function length_iter(a, count) {
    return is_null(a)
      ? count
      : length_iter(tail(a), count + 1);
  }
  return length_iter(items, 0);
}
```

</Prose>

<Example index={2} file="list_ref.sicp" source={listRefProgram} anim="calls">

Each call receives the tail of the list its caller had, so the argument shrinks by one pair per box: four calls to reach item 3 of `squares`, and five for the length of `odds`, the last on the empty list. The values print in box notation because that is what the call really receives.

</Example>

<Prose>

Another conventional technique is to build an answer list by adjoining elements to the front with `pair` while walking down a list with `tail`. To `append` two lists `list1` and `list2`: if `list1` is empty, the result is just `list2`; otherwise append the tail of `list1` to `list2` and adjoin the head of `list1` to the result.

</Prose>

<Example index={3} file="append.sicp" source={appendProgram} anim="pairs">

`append(squares, odds)` has nine pairs: five new ones copying `squares`, followed by the four of `odds`, shared rather than copied. The order of the arguments decides which list comes first and which is copied.

</Example>

<Prose>

**Mapping over lists.** One extremely useful operation applies some transformation to each element of a list and makes the list of results. `scale_list` multiplies each number in a list by a factor. The general idea is a common pattern, which we can capture as a higher-order function, as in §1.3. That function is `map`: it takes a function of one argument and a list, and returns the list of the results of applying the function to each element. Now `scale_list` is one line:

```js
function scale_list(items, factor) {
  return map(x => x * factor, items);
}
```

</Prose>

<Example index={4} file="map.sicp" source={mapProgram} anim="pairs">

`map` returns a new list with the same number of pairs as the one it was given. `math_abs` is a primitive and `x => x * x` a lambda expression; to `map` they are just functions. The list library declares the same `map`, so later programs use it without declaring it.

</Example>

<Prose>

`map` captures a common pattern, but it matters more because it establishes a higher level of abstraction for dealing with lists. In the first `scale_list`, the recursive structure draws attention to the element-by-element processing. Written with `map`, that detail is suppressed: scaling is a transformation of a list of elements into a list of results. The computer performs the same process either way; we think about it differently. `map` is an abstraction barrier that isolates functions that transform lists from the details of how elements are extracted and combined. Like the barriers of §2.1.2, it leaves us free to change how sequences are implemented while keeping the conceptual framework of operations that transform sequences into sequences. Section 2.2.3 builds a way of organising programs on this.

</Prose>

<Exercise id="2.17">

Declare a function `last_pair` that returns the list that contains only the last element of a given (nonempty) list. `last_pair(list(23, 72, 149, 34))` is `list(34)`.

<Solution>

**Solution.** A list whose tail is `null` is its own last pair; any other list's last pair is the last pair of its tail. The function returns the actual last pair of its argument, not a copy, so `last_pair(xs) === tail(tail(xs))` for a list of three.

</Solution>

<Exercise id="2.18">

Declare a function `reverse` that takes a list as argument and returns a list of the same elements in reverse order. `reverse(list(1, 4, 9, 16, 25))` is `list(25, 16, 9, 4, 1)`.

<Solution>

**Solution.** Walk down the list with an accumulator, adjoining each head to the front of the result so far. The first element is adjoined first and so ends up last. The process is iterative, and it is how the library's `reverse` is written.

</Solution>

Consider the change-counting program of §1.2.2. It would be nice to be able to change the currency easily, to count the ways to change a British pound, for example. As written, knowledge of the currency is spread between `first_denomination` and `count_change`, which knows there are five kinds of US coin. It would be nicer to supply a list of coins.

Rewrite `cc` so that its second argument is a list of the values of the coins to use rather than an integer:

const us_coins = list(50, 25, 10, 5, 1);
const uk_coins = list(100, 50, 20, 10, 5, 2, 1);
cc(100, us_coins);

The new `cc` has the same form as the old one, but it accesses its second argument through `first_denomination`, `except_first_denomination` and `no_more`. Declare these three in terms of primitive operations on list structure. Does the order of the list `coin_values` affect the answer produced by `cc`? Record your answer as `order_matters`.

**Solution.** The three are `head`, `tail` and `is_null` under new names. <Exercise id="2.20">

In the presence of higher-order functions, functions need not have more than one parameter. If a function such as `plus` naturally takes two arguments, we can write a variant to which we pass the arguments one at a time: applying it to the first argument returns a function that we apply to the second, and so on. This practice is called *currying*, after the logician Haskell Brooks Curry, and is common in languages such as Haskell and OCaml. In JavaScript, a curried `plus` is

```js
function plus_curried(x) {
  return y => x + y;
}
```

Write a function `brooks` that takes a curried function as its first argument and as its second a list of arguments, to which the curried function is applied one by one, in order. `brooks(plus_curried, list(3, 4))` should have the same effect as `plus_curried(3)(4)`.

While we are at it, curry `brooks` itself: write `brooks_curried`, applied as `brooks_curried(list(plus_curried, 3, 4))`. What are the results of evaluating the following two statements? Predict them, then record them as `result_1` and `result_2`.

```js
brooks_curried(list(brooks_curried,
                    list(plus_curried, 3, 4)));

brooks_curried(list(brooks_curried,
                    list(brooks_curried,
                         list(plus_curried, 3, 4))));
```

<Solution>

**Solution.** `brooks(f, args)` returns `f` when `args` is empty and otherwise `brooks(f(head(args)), tail(args))`. `brooks_curried(xs)` is `brooks(head(xs), tail(xs))`. Both statements are 7. In the first, `brooks_curried` is applied to the single argument `list(plus_curried, 3, 4)`, which is exactly the application shown before. The second unwraps one more layer in the same way.

</Solution>
</Exercise>

<Exercise id="2.22">

Louis Reasoner tries to rewrite the first `square_list` of Exercise 2.21 so that it evolves an iterative process:

```js
function square_list(items) {
  function iter(things, answer) {
    return is_null(things)
      ? answer
      : iter(tail(things),
             pair(square(head(things)),
                  answer));
  }
  return iter(items, null);
}
```

Unfortunately, this produces the answer list in the reverse order of the one desired. Why? Louis then tries to fix the bug by interchanging the arguments to `pair`, and that does not work either. Explain. Then record what Louis's first version returns for `list(1, 2, 3)` as `louis_result`, and write a `square_list` that is iterative and gets the order right.

<Solution>

**Solution.** `iter` takes elements from the front of `things` and adjoins each to the front of `answer`, so the first square is adjoined first and ends up last: `list(9, 4, 1)`. That is a stack, not a queue. Interchanging the arguments of `pair` keeps the order but breaks the structure: the result's head is the list so far and its tail is a number, `[[[null, 1], 4], 9]`, which is not a list at all. Two iterative repairs work: build the reversed list and `reverse` it at the end, or walk down the reversed input.

</Solution>
</Exercise>
<Exercise id="2.23">

The function `for_each` is similar to `map`. It takes a function and a list of elements, but rather than forming a list of the results it just applies the function to each element in turn, from left to right. The values the function returns are not used: `for_each` is used with functions that perform an action, such as printing.

```js
for_each(x => display(x), list(57, 321, 88));
```

prints 57, 321 and 88. The value returned by `for_each` can be something arbitrary, such as `true`. Give an implementation of `for_each`.

<Solution>

**Solution.** For an empty list, return `true`. Otherwise apply the function to the head and then call `for_each` on the tail. A conditional *statement* fits better than a conditional expression here, because the application to the head is evaluated only for its effect.

</Solution>
</Exercise>
