<Prose>

Delayed streams give us much of what local state and assignment gave us in §3.1, without dragging in the difficulties assignment brought along. They also let us draw the boundaries between modules in new places. A system built around state variables looks at one moment at a time: what is the value now? A system built from streams can take a whole time series, a signal, as one thing to hold, pass around and compare, so values from different moments are as easy to combine as values from one.

## Formulating iterations as stream processes

In §1.2.1 an iterative process was a handful of state variables updated over and over. We can now picture that state differently: not as variables that change, but as one stream that lists every value they ever take. Take the square-root method of §1.1.7 again. It improves a guess for √*x* by averaging it with *x* divided by it,

```js
function sqrt_improve(guess, x) {
  return average(guess, x / guess);
}
```

and where `sqrt_iter` kept the current guess in a parameter, we can instead produce the infinite stream of all the guesses, beginning with 1:

</Prose>

<Example index={0} file="sqrt_stream.sicp" source={paradigmSqrtStreamProgram} anim="series">

Each element is `sqrt_improve` applied to the one before, so the plot jumps from 1 to 1.5 and then settles on √2 ≈ 1.41421 within four steps. The streams of this section are infinite, so our `display_stream` takes a second argument, how many elements to print. Ask for 10 instead of 6: the extra points sit on the same line, because the guesses have stopped changing in the digits we can see.

</Example>

<Prose>

The stream holds every guess at once, so a function that keeps reading it until two neighbours agree closely enough would give a square root to any tolerance we like; exercise 3.64 writes it.

Another iteration fits the same mould. In §1.3.1 we summed the alternating series

π / 4 = 1 − 1/3 + 1/5 − 1/7 + ⋯

As a stream, this is three steps: the stream of summands (the reciprocals of the odd numbers with alternating signs), the stream of its partial sums (`partial_sums` from exercise 3.55), and that stream scaled by 4:

```js
function pi_summands(n) {
  return pair(1 / n, () => stream_map(x => -x, pi_summands(n + 2)));
}
const pi_stream = scale_stream(partial_sums(pi_summands(1)), 4);
```

The approximations it produces do approach π, but they crawl. After eight terms we only know that π lies somewhere between 3.284 and 3.017.

So far a stream of states has been just another way to write a loop. But because the whole history is a value, we can also *transform* it. A *sequence accelerator* turns a sequence of approximations into a new sequence that converges to the same limit, faster. One, due to Leonhard Euler, suits the partial sums of alternating series particularly well: if *S*ₙ is the *n*th partial sum, the accelerated sequence has terms

*S*ₙ₊₁ − (*S*ₙ₊₁ − *S*ₙ)² / (*S*ₙ₋₁ − 2*S*ₙ + *S*ₙ₊₁)

Since each term needs three neighbouring elements of the original, `euler_transform` reads them with `stream_ref` and moves along by one:

```js
function euler_transform(s) {
  const s0 = stream_ref(s, 0); // S(n-1)
  const s1 = stream_ref(s, 1); // S(n)
  const s2 = stream_ref(s, 2); // S(n+1)
  return pair(s2 - square(s2 - s1) / (s0 + (-2) * s1 + s2),
              memo(() => euler_transform(stream_tail(s))));
}
```

The tail is memoized (§3.5.1), because what comes next reads the transformed streams many times over.

Nothing stops us from accelerating the accelerated sequence, and then accelerating that. `make_tableau` builds a stream of streams, each the transform of the one before:

```js
function make_tableau(transform, s) {
  return pair(s, () => make_tableau(transform, transform(s)));
}
```

which we can picture as a triangle,

```
s00  s01  s02  s03  s04  ...
     s10  s11  s12  s13  ...
          s20  s21  s22  ...
                    ...
```

and the first element of each row, taken in turn, is a new sequence:

```js
function accelerated_sequence(transform, s) {
  return stream_map(head, make_tableau(transform, s));
}
```

Here are all three, side by side.

</Prose>

<Example index={1} file="pi_stream.sicp" source={paradigmPiStreamProgram} anim="series">

Three series, eight terms each. `pi_stream` zigzags around π and is still off by more than 0.1 at the end; `euler` starts within 0.03 of π and ends within 0.0004; `accelerated` agrees with π to 13 decimal places by its eighth term. Matching that with the plain partial sums would take on the order of 10¹³ terms, since the error of a partial sum is about the size of the next term. Each `display("...")` starts a new series in the plot; try plotting only `accelerated` and `euler` to see how differently they converge once the slow one is out of the scale. </Example>

<Prose>

None of this needs streams; the same arithmetic could be written with loops and variables. What streams add is convenience: the entire sequence of states is a data structure, so one uniform set of operations (map, transform, take the heads) builds even a tableau of sequences in a few lines.

## Infinite streams of pairs

In §2.2.3 sequences turned nested loops into pipelines over sequences of pairs. With infinite streams the same idea can range over an infinite set, which no loop can do. Suppose we want the `prime_sum_pairs` of §2.2.3 without an upper bound: the stream of all pairs of positive integers (*i*, *j*) with *i* ≤ *j* whose sum is prime. If `int_pairs` were the stream of all pairs with *i* ≤ *j* (each pair a two-element list, as in §2.2.3), we could simply filter it:

```js
stream_filter(p => is_prime(head(p) + head(tail(p))), int_pairs);
```

The interesting part is `int_pairs`. More generally, take two streams *S* and *T* and the infinite array of their pairs (*S*ᵢ, *T*ⱼ). We want those on or above the diagonal, *i* ≤ *j*. Call that stream `pairs(S, T)` and split it into three parts: the pair (*S*₀, *T*₀); the rest of the first row; and everything below the first row, which is `pairs` again, of the two tails.

</Prose>

<PairsDecompositionDiagram caption={<p>The third part is the same problem one size down, so <code>pairs</code> can call itself for it. The second part is <code>stream_map(x =&gt; list(head(s), x), stream_tail(t))</code>.</p>} />

<Prose>

That gives a function with one decision left open, how to combine the second and third parts:

```js
function pairs(s, t) {
  return pair(list(head(s), head(t)),
              () => combine_in_some_way(
                      stream_map(x => list(head(s), x), stream_tail(t)),
                      pairs(stream_tail(s), stream_tail(t))));
}
```

An obvious candidate is `stream_append`, the stream version of `append` (it is in the library):

```js
function stream_append(s1, s2) {
  return is_null(s1)
    ? s2
    : pair(head(s1), () => stream_append(stream_tail(s1), s2));
}
```

It will not do for infinite streams. `stream_append` hands over every element of its first stream before it even looks at the second, and here the first stream, the rest of row 1, never runs out.

</Prose>

<Example index={2} file="pairs_append.sicp" source={paradigmAppendPairsProgram} anim="pairs-order">

Thirty-one pairs, and every one of them is (1, *j*): the grid on the left fills its first row and then the pairs run off the edge, while the rows below stay dark. The grid on the right shows the same number of pairs from the interleaving version below, for comparison. Ask for 1000 pairs and you still never see (2, 2).

</Example>

<Prose>

We need a way of combining two streams that is guaranteed to reach every element of both, however long we wait for it. A neat one is to take elements from the two streams alternately:

```js
function interleave(s1, s2) {
  return is_null(s1)
    ? s2
    : pair(head(s1), () => interleave(s2, stream_tail(s1)));
}
```

Each call puts one element from its first argument out front and then swaps the roles of the two streams, so the second stream gets every other turn even if the first is infinite. (The precise property we need is that the pair of element *i* of one stream and element *j* of the other lands at some definite position *f*(*i*, *j*) of the result. David Turner used interleaving this way in his language KRC.) With it, `pairs` is complete:

```js
function pairs(s, t) {
  return pair(list(head(s), head(t)),
              () => interleave(stream_map(x => list(head(s), x),
                                          stream_tail(t)),
                               pairs(stream_tail(s), stream_tail(t))));
}
```

</Prose>

<Example index={3} file="pairs.sicp" source={paradigmPairsProgram} anim="pairs-order">

Watch the order in which the cells light up. Row 1 gets every second turn, row 2 every second turn of what is left (every fourth overall), row 3 every eighth, and so on: the 31st pair is (5, 5), the last cell of the triangle up to 5. The caption gives each pair's position as a formula; exercise 3.66 asks you to find it. Change the 31 to 63 and the triangle up to (6, 6) is complete.

</Example>

<Prose>

And now `prime_sum_pairs` over all the integers is a filter on `int_pairs`, exactly as planned:

## Streams as signals

We first described streams as the programming counterpart of signals in signal-processing systems, and we can use them to model such systems quite literally, with the elements of a stream standing for the values of a signal at equally spaced moments. An *integrator* or *summer*, for instance, takes an input stream *x* = (*x*ᵢ), an initial value *C* and a small time step *dt*, and produces the running sum

*S*ᵢ = *C* + Σⱼ₌₁ⁱ *x*ⱼ *dt*

as the stream *S* = (*S*ᵢ). Written the way §3.5.2 wrote `integers`, implicitly, in terms of itself:

```js
function integral(integrand, initial_value, dt) {
  const integ = pair(initial_value,
                     () => add_streams(scale_stream(integrand, dt),
                                       integ));
  return integ;
}
```

</Prose>

<SignalIntegralDiagram caption={<p>The input is scaled by <em>dt</em> and goes through an adder, and the adder's output, with the initial value in front, is both the result and the adder's other input. The loop in the picture is the self-reference in the declaration of <code>integ</code>.</p>} />

<Example index={5} file="integral.sicp" source={paradigmIntegralProgram} anim="series" budget={300000}>

The integrand is the stream of times 0, 0.01, 0.02, …, so the integral should be *t*² / 2. The plot shows every 25th element of both: the computed sum runs just below the exact curve, because each step adds the value at the start of its interval. At *t* = 3 the program gives 4.485 instead of 4.5, an error of 3 *dt* / 2; make `dt` ten times smaller and the error shrinks tenfold (raise the budget, since there are ten times as many steps). Our `integral` memoizes the tail of `integ`, so that every element is computed once.

</Example>
