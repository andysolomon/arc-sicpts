<Prose>

Now for the reason we built the environment model: objects with local state. Take the withdrawal processor of §3.1.1. `make_withdraw` takes a starting balance and returns a function that withdraws from it:

```js
function make_withdraw(balance) {
  return amount => {
           if (balance >= amount) {
             balance = balance - amount;
             return balance;
           } else {
             return "insufficient funds";
           }
         };
}
```

We will follow `const W1 = make_withdraw(100);` and then `W1(50);`.

Declaring `make_withdraw` is nothing new: the program frame gets a function object whose environment is the program environment. The only unusual thing about it is that its body returns a lambda expression.

The interesting step is the call `make_withdraw(100)`. As always, it creates a frame, E1, binding the parameter `balance` to 100 and extending the program environment. In E1 the body is evaluated, and the body is `return` of a lambda expression. Evaluating that lambda expression makes a new function object, whose code is the lambda's and whose environment is *E1*, because E1 is where it was evaluated. That object is the value of the call, and the declaration binds it to `W1` in the program frame, where the declaration itself was evaluated. Step through it below and look at the row for `W1`: its environment bubble points at E1, the frame holding `balance`.

</Prose>

<Example index={0} mode="step" file="make_withdraw.sicp" source={envModelMakeWithdrawProgram} anim="frames">

After `const W1 = ...` the call `make_withdraw(100)` has returned, yet E1 stays bright: the function bound to `W1` points into it, so it is still part of the environment structure. `W1(50)` then makes E2, which extends E1, not E0. Step to the assignment and watch it search outward from E2 and change `balance` in E1.

</Example>

<Prose>

Now apply `W1` to 50. A new frame binds `amount`, the parameter of the function, to 50. What matters is the frame's enclosing environment: it is E1, not the program environment, because E1 is the environment carried by the `W1` function object. The body tests `balance >= amount`: `amount` is found in the new frame, and `balance` one frame out, in E1.

The assignment `balance = balance - amount` then changes the binding of `balance` in E1, the first frame that has one. When the call returns, `balance` is 50, and E1 is still pointed to by `W1`. The frame that bound `amount` has served its purpose: the call that made it is over and nothing points to it, so it can be forgotten. The next call of `W1` will make a fresh frame for `amount`, again extending E1. That makes E1 the *place* where `W1` keeps its local state.

What happens when we make a second withdrawal processor?

</Prose>

<Example index={1} file="two_withdraws.sicp" source={envModelTwoWithdrawsProgram} anim="frames">

`make_withdraw(100)` runs twice, so there are two frames binding `balance`, E1 for `W1` and E3 for `W2`, and the two function objects point to different ones. Withdrawing 70 through `W2` leaves `W1`'s balance alone: the final `W1(40)` still starts from 50. The two rows in E0 even show the same parameters, `(amount)`; only the environment pointers differ.

</Example>

<Prose>

`W2` is a function object like `W1`: a pair of code and environment. Its environment, the frame made by the second call of `make_withdraw`, has its own binding of `balance`. Its code is the same as `W1`'s, the lambda expression in the body of `make_withdraw`. That is the whole explanation of why `W1` and `W2` are independent objects: each call of one of them evaluates the same code in an environment that reaches a different `balance`, so changing one balance cannot affect the other.

Whether two such objects literally share the code in memory or each have a copy is up to the implementation. In the evaluator of Chapter 4, as in the Laboratory, it is shared.

</Prose>

<Exercise id="3.10">

In `make_withdraw`, the local variable `balance` is the function's parameter. It can also be created separately, by applying a lambda expression immediately, which §1.3.2 showed is how a local name can be made without a declaration:

```js
function make_withdraw(initial_amount) {
  return (balance =>
            amount => {
              if (balance >= amount) {
                balance = balance - amount;
                return balance;
              } else {
                return "insufficient funds";
              }
            })(initial_amount);
}
```

Write this version of `make_withdraw` and show that it makes objects with the same behaviour as the original. Then use the environment model on `const W1 = make_withdraw(100); W1(50); const W2 = make_withdraw(100);` and answer: how many frames does one call of `make_withdraw` create now, which name is bound in the frame `W1`'s environment pointer leads to, and which name in the frame that one extends?

<Solution>

**Solution.** The behaviour is the same, but the structure has one more frame per object. `make_withdraw(100)` first makes a frame binding `initial_amount` to 100. Its body applies the outer lambda to `initial_amount`, which makes a second frame, binding `balance` to 100 and extending the first. The inner lambda expression is evaluated in that second frame, so `W1` points at the frame of `balance`, which in turn extends the frame of `initial_amount`. Withdrawals change `balance`; `initial_amount` stays 100 forever, unused. `W2` gets its own pair of frames. Paste the solution into an editor above to see the chain E0 ← `initial_amount` ← `balance` ← `amount`. Declaring `let balance = initial_amount;` in the body instead would give the same shape in this Laboratory, since a body block with declarations gets a frame of its own (§3.2.4); the check here asks for the lambda version.

</Solution>
</Exercise>
