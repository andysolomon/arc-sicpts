The representation of §5.3.1 solves the problem of implementing list structure, provided that we have an infinite amount of memory. With a real computer we will eventually run out of free space in which to construct new pairs. (Perhaps not always: at one `pair` per nanosecond, about 10¹⁸ cells would last thirty years. But processors keep getting faster, and many of them may share one memory.) However, most of the pairs generated in a typical computation are used only to hold intermediate results. After these results are accessed, the pairs are no longer needed: they are *garbage*. For instance, the computation

```js
accumulate((x, y) => x + y,
           0,
           filter(is_odd, enumerate_interval(0, n)))
```

constructs two lists, the enumeration and the result of filtering it. When the accumulation is complete, these lists are no longer needed, and the memory allocated to them can be reclaimed. If we can arrange to collect all the garbage periodically, and if this turns out to recycle memory at about the same rate at which we construct new pairs, we will have preserved the illusion that there is an infinite amount of memory.

To recycle pairs, we must have a way to determine which allocated pairs are not needed, in the sense that their contents can no longer influence the future of the computation. The method we examine is *garbage collection*. It is based on the observation that, at any moment in an interpretation based on list-structured memory, the only objects that can affect the future of the computation are those that can be reached by some succession of `head` and `tail` operations starting from the pointers currently in the machine registers. (We assume the stack is a list as in §5.3.1, so items on the stack are reachable from the stack register.) Any memory cell that is not so accessible may be recycled.

There are many ways to perform garbage collection. The method we examine here is called *stop-and-copy*. The basic idea is to divide memory into two halves, working memory and free memory. When `pair` constructs pairs, it allocates them in working memory. When working memory is full, we perform garbage collection by locating all the useful pairs in working memory, tracing all the `head` and `tail` pointers starting with the machine registers, and copying them into consecutive locations in free memory. Since we do not copy the garbage, there will presumably be additional free memory that we can use for new pairs. Nothing in the working memory is needed any more, since all the useful pairs in it have been copied. So if we interchange the roles of working memory and free memory, we can continue processing: new pairs are allocated in the new working memory, which was the old free memory, and when that is full we copy the useful pairs into the new free memory, which was the old working memory.

The idea was invented by Minsky for the Lisp of the PDP-1 at MIT, developed by Fenichel and Yochelson (1969) for Multics, made real-time by Baker (1978), and extended by Lieberman and Hewitt (1983) to take advantage of the fact that some structure is more volatile and other structure more permanent. The common alternative is *mark-sweep*: trace all the structure accessible from the registers, marking each pair reached, then scan all of memory and sweep up every unmarked location for reuse. Stop-and-copy examines only the useful part of memory, where mark-sweep must sweep all of it. It is also a *compacting* collector: at the end, the useful data occupy consecutive locations, with all garbage pairs squeezed out, which matters on machines with virtual memory, where accesses to widely separated addresses may require extra paging.

## Implementation of a stop-and-copy garbage collector

We now use our register-machine language to describe the stop-and-copy algorithm in more detail. We assume a register called `root` that contains a pointer to a structure that eventually points at all accessible data. This can be arranged by storing the contents of all the machine registers in a preallocated list pointed at by `root` just before starting garbage collection. (The list leaves out the registers of the storage-allocation system itself: `root`, `the_heads`, `the_tails` and the others introduced below.) In addition to the current working memory, there is free memory into which we can copy the useful data. The current working memory consists of vectors whose base addresses are in registers called `the_heads` and `the_tails`, and the free memory is in registers called `new_heads` and `new_tails`.

Garbage collection is triggered when we exhaust the free cells in the current working memory, that is, when a `pair` operation attempts to increment the `free` pointer beyond the end of the memory vector. When it is complete, the `root` pointer will point into the new memory, all objects accessible from `root` will have been moved there, and `free` will indicate the next place in the new memory where a new pair can be allocated. The roles of working memory and new memory will have been interchanged: new pairs are constructed in the new memory, beginning at `free`, and the previous working memory is available as the new memory for the next garbage collection.

The state of the garbage-collection process is controlled by two pointers, `free` and `scan`, initialized to point to the beginning of the new memory. The algorithm begins by relocating the pair pointed at by `root` to the beginning of the new memory. The pair is copied, the `root` pointer is adjusted to point to the new location, and `free` is incremented. In addition, the old location of the pair is marked to show that its contents have been moved: in the head position we place a special tag that signals an already-moved object, traditionally called a *broken heart*, and in the tail position a *forwarding address* that points at the location to which the object has been moved.

After relocating the root, the collector enters its basic cycle. At each step, `scan`, initially pointing at the relocated root, points at a pair that has been moved to the new memory but whose head and tail still refer to objects in the old memory. These objects are each relocated, and `scan` is incremented. To relocate an object, for example the one indicated by the head of the pair we are scanning, we check whether it has already been moved, as indicated by a broken heart in its head position. If it has not, we copy it to the place indicated by `free`, update `free`, set up a broken heart at the object's old location, and update the pointer to the object (here, the head of the pair being scanned) to point to the new location. If it has already been moved, its forwarding address, found in the tail of the broken heart, is substituted for the pointer in the pair being scanned. Eventually all accessible objects will have been moved and scanned, at which point `scan` overtakes `free` and the process terminates.

The basic step of relocating an object is a subroutine called `relocate_old_result_in_new`. It gets its argument, a pointer to the object to be relocated, from a register named `old`. It relocates the designated object, incrementing `free` in the process, puts a pointer to the relocated object into a register called `new`, and returns by branching to the entry point stored in the register `relocate_continue`. To begin garbage collection, we invoke this subroutine to relocate the `root` pointer, after initializing `free` and `scan`. When the relocation of `root` has been accomplished, we install the new pointer as the new `root` and enter the main loop.

```js
"begin_garbage_collection",
  assign("free", constant(0)),
  assign("scan", constant(0)),
  assign("old", reg("root")),
  assign("relocate_continue", label("reassign_root")),
  go_to(label("relocate_old_result_in_new")),
"reassign_root",
  assign("root", reg("new")),
  go_to(label("gc_loop")),
```

In the main loop we must determine whether there are any more objects to be scanned, by testing whether `scan` coincides with `free`. If it does, all accessible objects have been relocated, and we branch to `gc_flip`, which cleans things up so that we can continue the interrupted computation. If there are still pairs to be scanned, we call the relocate subroutine to relocate the head of the next pair, by placing the head pointer in `old`. The `relocate_continue` register is set up so that the subroutine returns to update the head pointer.

```js
"gc_loop",
  test(list(op("==="), reg("scan"), reg("free"))),
  branch(label("gc_flip")),
  assign("old", list(op("vector_ref"), reg("new_heads"), reg("scan"))),
  assign("relocate_continue", label("update_head")),
  go_to(label("relocate_old_result_in_new")),
```

At `update_head`, we modify the head pointer of the pair being scanned, then proceed to relocate its tail. We return to `update_tail` when that relocation has been accomplished. After relocating and updating the tail, we are finished scanning that pair, so we continue with the main loop.

```js
"update_head",
  perform(list(op("vector_set"),
               reg("new_heads"), reg("scan"), reg("new"))),
  assign("old", list(op("vector_ref"),
                     reg("new_tails"), reg("scan"))),
  assign("relocate_continue", label("update_tail")),
  go_to(label("relocate_old_result_in_new")),

"update_tail",
  perform(list(op("vector_set"),
               reg("new_tails"), reg("scan"), reg("new"))),
  assign("scan", list(op("+"), reg("scan"), constant(1))),
  go_to(label("gc_loop")),
```

The subroutine `relocate_old_result_in_new` relocates objects as follows. If the object to be relocated (pointed at by `old`) is not a pair, we return the same pointer unchanged in `new`: if we are scanning a pair whose head is the number 4, represented by `n4`, the relocated head should still be `n4`. Otherwise we must perform the relocation. If the head position of the pair to be relocated contains a broken heart, the pair has already been moved, so we retrieve the forwarding address from the tail of the broken heart and return it in `new`. If `old` points at a yet-unmoved pair, we move the pair to the first free cell in new memory (pointed at by `free`) and set up the broken heart by storing a broken-heart tag and forwarding address at the old location. The subroutine uses a register `oldht` to hold the head or the tail of the object pointed at by `old`. It tests with the low-level predicate `is_pointer_to_pair` rather than `is_pair`, because in a real system there might be things that are treated as pairs for garbage-collection purposes, such as function objects implemented as a special kind of pair that does not satisfy `is_pair`.

```js
"relocate_old_result_in_new",
  test(list(op("is_pointer_to_pair"), reg("old"))),
  branch(label("pair")),
  assign("new", reg("old")),
  go_to(reg("relocate_continue")),
"pair",
  assign("oldht", list(op("vector_ref"),
                       reg("the_heads"), reg("old"))),
  test(list(op("is_broken_heart"), reg("oldht"))),
  branch(label("already_moved")),
  assign("new", reg("free")),     // new location for pair
  // Update free pointer
  assign("free", list(op("+"), reg("free"), constant(1))),
  // Copy the head and tail to new memory
  perform(list(op("vector_set"),
               reg("new_heads"), reg("new"),
               reg("oldht"))),
  assign("oldht", list(op("vector_ref"),
                       reg("the_tails"), reg("old"))),
  perform(list(op("vector_set"),
               reg("new_tails"), reg("new"),
               reg("oldht"))),
  // Construct the broken heart
  perform(list(op("vector_set"),
               reg("the_heads"), reg("old"),
               constant("broken_heart"))),
  perform(list(op("vector_set"),
               reg("the_tails"), reg("old"),
               reg("new"))),
  go_to(reg("relocate_continue")),
"already_moved",
  assign("new", list(op("vector_ref"),
                     reg("the_tails"), reg("old"))),
  go_to(reg("relocate_continue")),
```

At the very end of the garbage-collection process, we interchange the roles of old and new memories by interchanging pointers: `the_heads` with `new_heads`, and `the_tails` with `new_tails`. We will then be ready to perform another garbage collection the next time memory runs out.

```js
"gc_flip",
  assign("temp", reg("the_tails")),
  assign("the_tails", reg("new_tails")),
  assign("new_tails", reg("temp")),
  assign("temp", reg("the_heads")),
  assign("the_heads", reg("new_heads")),
  assign("new_heads", reg("temp"))
```

The Laboratory's own evaluator never runs this collector. Its pairs are JavaScript arrays, and JavaScript's collector reclaims them when nothing refers to them. What `collectGarbage` models is the algorithm: it takes the image of a finished program's pairs, builds the root list from the program's names (standing in for the registers), and runs `gcControllerSource`, the controller above word for word, on the Laboratory's register-machine simulator, with `vector_ref`, `vector_set`, `is_pointer_to_pair` and `is_broken_heart` as operations on vectors of typed pointers. It collects once, at the end, rather than when `free` reaches the end of memory, and new memory is as large as working memory. `chapter-5/section-5-3.test.ts` asserts eight pairs before and five after for the first program, two broken hearts followed, and two survivors out of twelve for the second; `chapter-5/memory.test.ts` asserts that sharing is preserved.
