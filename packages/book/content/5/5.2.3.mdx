<Prose>

The assembler calls `make_execution_function` to generate the execution function for a controller instruction. Like the `analyze` function in the evaluator of §4.1.7, this dispatches on the type of instruction to generate the appropriate execution function. The details of these execution functions determine the meaning of the individual instructions in the register-machine language.

```js
const make_execution_function = (
    inst: Instruction,
    labels: List<LabelEntry>,
    machine: Machine,
    pc: Register,
    flag: Register,
    stack: Stack,
    ops: Operations
): ExecutionFunction =>
    type(inst) === "assign"
    ? make_assign_ef(inst, machine, labels, ops, pc)
    : type(inst) === "test"
    ? make_test_ef(inst, machine, labels, ops, flag, pc)
    : type(inst) === "branch"
    ? make_branch_ef(inst, machine, labels, flag, pc)
    : type(inst) === "go_to"
    ? make_go_to_ef(inst, machine, labels, pc)
    : type(inst) === "save"
    ? make_save_ef(inst, machine, stack, pc)
    : type(inst) === "restore"
    ? make_restore_ef(inst, machine, stack, pc)
    : type(inst) === "push_marker_to_stack"
    ? make_push_marker_to_stack_ef(machine, stack, pc)
    : type(inst) === "revert_stack_to_marker"
    ? make_revert_stack_to_marker_ef(machine, stack, pc)
    : type(inst) === "perform"
    ? make_perform_ef(inst, machine, labels, ops, pc)
    : error(inst, "unknown instruction type -- assemble");
```

The elements of the controller sequence received by `make_machine` and passed to `assemble` are strings (for labels) and tagged lists (for instructions). The tag in an instruction is a string that identifies the instruction type, such as `"go_to"`, and the remaining elements of the list contain the arguments, such as the destination of the `go_to`. The dispatch in `make_execution_function` uses

```js
const type = (instruction: Instruction): string => head(instruction);
```

The tagged lists are constructed when the `list` expression that is the third argument to `make_machine` is evaluated. Each argument to that `list` is either a string (which evaluates to itself) or a call to a constructor for an instruction tagged list. For example, `assign("b", reg("t"))` calls the constructor `assign` with arguments `"b"` and the result of calling the constructor `reg` with the argument `"t"`. The constructors and their arguments determine the syntax of the individual instructions in the register-machine language. The instruction constructors and selectors are shown below, along with the execution-function generators that use the selectors.

## The instruction `assign`

`make_assign_ef` makes execution functions for `assign` instructions:

```js
const make_assign_ef = (
    inst: Instruction,
    machine: Machine,
    labels: List<LabelEntry>,
    operations: Operations,
    pc: Register
): ExecutionFunction => {
    const target = get_register(machine, assign_reg_name(inst));
    const value_exp = assign_value_exp(inst);
    const value_fun =
        is_operation_exp(value_exp)
        ? make_operation_exp_ef(value_exp, machine, labels, operations)
        : make_primitive_exp_ef(value_exp, machine, labels);
    return () => {
               set_contents(target, value_fun());
               advance_pc(pc);
           };
};
```

The function `assign` constructs `assign` instructions. The selectors `assign_reg_name` and `assign_value_exp` extract the register name and value expression from an `assign` instruction.

```js
const assign = (register_name: string, source: Instruction): Instruction =>
    list("assign", register_name, source);
const assign_reg_name = (assign_instruction: Instruction): string =>
    head(tail(assign_instruction));
const assign_value_exp = (assign_instruction: Instruction): Instruction =>
    head(tail(tail(assign_instruction)));
```

`make_assign_ef` looks up the register name with `get_register` to produce the target register object. The value expression is passed to `make_operation_exp_ef` if the value is the result of an operation, and to `make_primitive_exp_ef` otherwise. These functions (shown below) analyze the value expression and produce an execution function for the value: a function of no arguments, called `value_fun`, which will be evaluated during the simulation to produce the actual value to be assigned to the register. Notice that the work of looking up the register name and analyzing the value expression is performed just once, at assembly time, not every time the instruction is simulated. This saving of work is the reason we use execution functions, and corresponds directly to the saving we obtained by separating program analysis from execution in the evaluator of §4.1.7.

The result returned by `make_assign_ef` is the execution function for the `assign` instruction. When this function is called (by the machine model's `execute` function), it sets the contents of the target register to the result obtained by executing `value_fun`. Then it advances the `pc` to the next instruction by running the function

```js
const advance_pc = (pc: Register): void => {
    set_contents(pc, tail(get_contents(pc)));
};
```

`advance_pc` is the normal termination for all instructions except `branch` and `go_to`.

## The instructions `test`, `branch` and `go_to`

`make_test_ef` handles `test` instructions in a similar way. It extracts the expression that specifies the condition to be tested and generates an execution function for it. At simulation time, the function for the condition is called, the result is assigned to the `flag` register, and the `pc` is advanced:

```js
const make_test_ef = (
    inst: Instruction,
    machine: Machine,
    labels: List<LabelEntry>,
    operations: Operations,
    flag: Register,
    pc: Register
): ExecutionFunction => {
    const condition = test_condition(inst);
    if (is_operation_exp(condition)) {
        const condition_fun = make_operation_exp_ef(
                                  condition, machine,
                                  labels, operations);
        return () => {
                   set_contents(flag, condition_fun());
                   advance_pc(pc);
               };
    } else {
        error(inst, "bad test instruction -- assemble");
    }
};

const test = (condition: Instruction): Instruction => list("test", condition);

const test_condition = (test_instruction: Instruction): Instruction =>
    head(tail(test_instruction));
```

The execution function for a `branch` instruction checks the contents of the `flag` register and either sets the contents of the `pc` to the branch destination (if the branch is taken) or else just advances the `pc` (if the branch is not taken). Notice that the indicated destination in a `branch` instruction must be a label, and `make_branch_ef` enforces this. Notice also that the label is looked up at assembly time, not each time the `branch` instruction is simulated.

```js
const make_branch_ef = (
    inst: Instruction,
    machine: Machine,
    labels: List<LabelEntry>,
    flag: Register,
    pc: Register
): ExecutionFunction => {
    const dest = branch_dest(inst);
    if (is_label_exp(dest)) {
        const insts = lookup_label(labels, label_exp_label(dest));
        return () => {
                   if (get_contents(flag)) {
                       set_contents(pc, insts);
                   } else {
                       advance_pc(pc);
                   }
               };
    } else {
        error(inst, "bad branch instruction -- assemble");
    }
};

const branch = (label: Instruction): Instruction => list("branch", label);

const branch_dest = (branch_instruction: Instruction): Instruction =>
    head(tail(branch_instruction));
```

A `go_to` instruction is similar to a branch, except that the destination may be specified either as a label or as a register, and there is no condition to check: the `pc` is always set to the new destination.

```js
const make_go_to_ef = (
    inst: Instruction,
    machine: Machine,
    labels: List<LabelEntry>,
    pc: Register
): ExecutionFunction => {
    const dest = go_to_dest(inst);
    if (is_label_exp(dest)) {
        const insts = lookup_label(labels, label_exp_label(dest));
        return () => set_contents(pc, insts);
    } else if (is_register_exp(dest)) {
        const reg = get_register(machine, register_exp_reg(dest));
        return () => set_contents(pc, get_contents(reg));
    } else {
        error(inst, "bad go_to instruction -- assemble");
    }
};

const go_to = (label: Instruction): Instruction => list("go_to", label);

const go_to_dest = (go_to_instruction: Instruction): Instruction =>
    head(tail(go_to_instruction));
```

## Other instructions

The stack instructions `save` and `restore` simply use the stack with the designated register and advance the `pc`:

```js
const make_save_ef = (
    inst: Instruction,
    machine: Machine,
    stack: Stack,
    pc: Register
): ExecutionFunction => {
    const reg = get_register(machine, stack_inst_reg_name(inst));
    return () => {
               push(stack, get_contents(reg));
               advance_pc(pc);
           };
};
const make_restore_ef = (
    inst: Instruction,
    machine: Machine,
    stack: Stack,
    pc: Register
): ExecutionFunction => {
    const reg = get_register(machine, stack_inst_reg_name(inst));
    return () => {
               set_contents(reg, pop(stack));
               advance_pc(pc);
           };
};

const save = (reg: string): Instruction => list("save", reg);

const restore = (reg: string): Instruction => list("restore", reg);

const stack_inst_reg_name = (stack_instruction: Instruction): string =>
    head(tail(stack_instruction));
```

The two marker instructions that §5.4 needs send the stack its `push_marker` and `pop_marker` requests (§5.2.1). `revert_stack_to_marker` throws away everything pushed since the most recent `push_marker_to_stack`.

```js
const make_push_marker_to_stack_ef = (machine: Machine, stack: Stack, pc: Register): ExecutionFunction =>
    () => {
        push_marker(stack);
        advance_pc(pc);
    };
const make_revert_stack_to_marker_ef = (machine: Machine, stack: Stack, pc: Register): ExecutionFunction =>
    () => {
        pop_marker(stack);
        advance_pc(pc);
    };

const push_marker_to_stack = (): Instruction => list("push_marker_to_stack");
const revert_stack_to_marker = (): Instruction => list("revert_stack_to_marker");
```

The final instruction type, handled by `make_perform_ef`, generates an execution function for the action to be performed. At simulation time, the action function is executed and the `pc` advanced.

```js
const make_perform_ef = (
    inst: Instruction,
    machine: Machine,
    labels: List<LabelEntry>,
    operations: Operations,
    pc: Register
): ExecutionFunction => {
    const action = perform_action(inst);
    if (is_operation_exp(action)) {
        const action_fun = make_operation_exp_ef(action, machine,
                                                 labels, operations);
        return () => {
                   action_fun();
                   advance_pc(pc);
               };
    } else {
        error(inst, "bad perform instruction -- assemble");
    }
};

const perform = (action: Instruction): Instruction => list("perform", action);

const perform_action = (perform_instruction: Instruction): Instruction =>
    head(tail(perform_instruction));
```

## Execution functions for subexpressions

The value of a `reg`, `label` or `constant` expression may be needed for assignment to a register (`make_assign_ef`, above) or for input to an operation (`make_operation_exp_ef`, below). The following function generates execution functions to produce values for these expressions during the simulation:

```js
const make_primitive_exp_ef = (
    exp: Instruction,
    machine: Machine,
    labels: List<LabelEntry>
): (() => unknown) => {
    if (is_constant_exp(exp)) {
        const c = constant_exp_value(exp);
        return () => c;
    } else if (is_label_exp(exp)) {
        const insts = lookup_label(labels, label_exp_label(exp));
        return () => insts;
    } else if (is_register_exp(exp)) {
        const r = get_register(machine, register_exp_reg(exp));
        return () => get_contents(r);
    } else {
        error(exp, "unknown expression type -- assemble");
    }
};
```

The syntax of `reg`, `label` and `constant` expressions is determined by the following constructors, along with corresponding predicates and selectors. `is_tagged_list` is the function of §4.1.2.

```js
const reg = (name: string): Instruction => list("reg", name);

const is_register_exp = (exp: Instruction): boolean => is_tagged_list(exp, "reg");

const register_exp_reg = (exp: Instruction): string => head(tail(exp));

const constant = (value: unknown): Instruction => list("constant", value);

const is_constant_exp = (exp: Instruction): boolean =>
    is_tagged_list(exp, "constant");

const constant_exp_value = (exp: Instruction): unknown => head(tail(exp));

const label = (name: string): Instruction => list("label", name);

const is_label_exp = (exp: Instruction): boolean => is_tagged_list(exp, "label");

const label_exp_label = (exp: Instruction): string => head(tail(exp));
```

The instructions `assign`, `perform` and `test` may include the application of a machine operation (specified by an `op` expression) to some operands (specified by `reg` and `constant` expressions). The following function produces an execution function for an operation expression, a list containing the operation and operand expressions from the instruction:

```js
const make_operation_exp_ef = (
    exp: Instruction,
    machine: Machine,
    labels: List<LabelEntry>,
    operations: Operations
): (() => unknown) => {
    const op = lookup_prim(operation_exp_op(exp), operations);
    const afuns = map(e => make_primitive_exp_ef(e, machine, labels),
                      operation_exp_operands(exp));
    return () => op(...map(f => f(), afuns));
};
```

The syntax of operation expressions is determined by

```js
const op = (name: string): Instruction => list("op", name);

const is_operation_exp = (exp: Instruction): boolean =>
    is_pair(exp) && is_tagged_list(head(exp), "op");

const operation_exp_op = (op_exp: Instruction): string => head(tail(head(op_exp)));

const operation_exp_operands = (op_exp: Instruction): List<Instruction> => tail(op_exp);
```

Observe that the treatment of operation expressions is very much like the treatment of function applications by `analyze_application` in the evaluator of §4.1.7, in that we generate an execution function for each operand. At simulation time, we call the operand functions and apply the JavaScript function that simulates the operation to the resulting values. We spread the list of their values into the call, `op(...map(f => f(), afuns))`, as `apply_primitive_function` did in §4.1.4, so that `op` receives all the elements of the list as separate arguments. Without the spread, `op` would be restricted to be a function of one argument.

The simulation function is found by looking up the operation name in the operation table for the machine:

```js
const lookup_prim = (symbol: string, operations: Operations): ((...args: List<unknown>) => unknown) => {
    const val = assoc(symbol, operations);
    return is_undefined(val)
           ? error(symbol, "unknown operation -- assemble")
           : head(tail(val));
};
```

<Exercise id="5.10">

When we introduced `save` and `restore` in §5.1.4, we didn't specify what would happen if you tried to restore a register that was not the last one saved, as in the sequence

```js
save(y);
save(x);
restore(y);
```

There are several reasonable possibilities for the meaning of `restore`:

- **a.** `restore(y)` puts into `y` the last value saved on the stack, regardless of what register that value came from. This is the way our simulator behaves. Show how to take advantage of this behavior to eliminate one instruction from the Fibonacci machine of §5.1.4. The starter's `fib_controller_short` is that machine's controller; remove one instruction.
- **b.** `restore(y)` puts into `y` the last value saved on the stack, but only if that value was saved from `y`; otherwise, it signals an error. Modify the simulator to behave this way. You will have to change `save` to put the register name on the stack along with the value. The editor holds `make_save_ef` and `make_restore_ef`.
- **c.** `restore(y)` puts into `y` the last value saved from `y`, regardless of what other registers were saved after `y` and not restored. Modify the simulator to behave this way. You will have to associate a separate stack with each register, and make the `initialize_stack` operation initialize all the register stacks.

The checker runs your controller from part (a) on the Laboratory's simulator, which behaves as in part (a), for Fib(6) and Fib(10) and counts its instructions. It checks part (b) by restoring in the right and in the wrong order, by running the original Fibonacci machine on your simulator, and by running your controller from part (a) on it, which must now fail. Part (c) changes `restore` again, in a way incompatible with part (b), so it is not checked; the solution describes it.

<Solution>

**Solution.** (a) At `afterfib_n_2`, `val` holds Fib(*n* − 2) and the top of the stack is Fib(*n* − 1), saved from `val`. The original moves `val` into `n` and then restores `val`; instead, `restore("n")` puts Fib(*n* − 1) straight into `n`, and `val` keeps Fib(*n* − 2). The sum is the same, and two instructions become one, 21 instead of 22.

(b) `make_save_ef` pushes `pair(name, value)`, and the execution function made by `make_restore_ef` pops a pair, compares its head with the register's name, and either sets the register to the tail or signals an error. The shortened controller from part (a) now fails at its first `restore("n")`, since the value was saved from `val`.

(c) Give each register its own stack, for example by making the register table hold a stack beside each register; `save` and `restore` find the stack with the register, and `initialize_stack` walks the register table initializing every stack. This part is not checked: parts (b) and (c) give `restore` incompatible meanings, and the editor holds one simulator.

</Solution>
