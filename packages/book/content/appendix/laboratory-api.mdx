<Prose>

The Laboratory is the TypeScript package `@sicp/lab`. The Book never evaluates code itself: it sends text to the Laboratory and draws the JSON that comes back. Everything on this page is exported from the package root.

</Prose>

## Evaluating

| Export | What it does |
| --- | --- |
| `parse(source)` | Text to syntax tree. Throws `SourceError` with a location. |
| `evaluate(source, options?)` | Runs to completion on the calling thread and returns an `Outcome`: `done`, `error` or `budget-exhausted`. Never throws for a program's own mistakes. |
| `prepare(source, options?)` | Parses and returns a `Machine` without running it. |
| `Machine.run(maxSteps?)` | Advances at most `maxSteps` steps and returns the status; `paused` means call again. |

Options are `budget` (steps, default 100 000), `prelude` (source evaluated first in an enclosing frame), `context` (declarations evaluated in the program's own frame before it, so that they call the program's functions), `display` (receives output lines), `draw` (receives each line drawn by `draw_line`, as a `Segment` `[x1, y1, x2, y2]`), `onMachine` (receives every register machine `make_machine` creates), `onPair` (receives every pair `pair` and `list` allocate, in order), `hooks` and `seed`. An error raised by code in the prelude says so, as `Hidden prelude, line N: …`.

Every program starts in a frame that extends two outer frames: `global`, which holds the primitives, and `library`, which holds the list and stream functions of Source §2 and §3 and the register-machine language of §5.1, written in Source (`evaluator/library.ts`). A declaration in the program shadows a library function of the same name. `createLibraryEnvironment(display)` returns that starting environment, which is how the CLI's REPL begins.

| Export | What it does |
| --- | --- |
| `toTaggedList(program)` | A syntax tree to the tagged lists of §4.1.2; the primitive `parse` uses it. |
| `metacircularPrelude`, `analyzingPrelude`, … | The evaluators of Chapter 4 as Source text, ready to be a prelude. |
| `omit(source, ...names)`, `pick(source, ...names)` | A program without, or with only, the named top-level declarations: how an exercise hides all of an evaluator except the functions the reader rewrites. |

## Register machines

| Export | What it does |
| --- | --- |
| `RegisterMachine` | The simulator behind `make_machine`, organised as in §5.2: `assemble(controller)` turns each instruction into an execution function, `start()` runs from the first instruction until the controller ends. Registers, a monitored stack with markers (`totalPushes`, `maxDepth`), an instruction count and observers that see every instruction. |
| `readController(list)`, `instructionText(value)` | The register-machine language as data: a controller list read into typed instructions, and instructions printed as the book writes them, e.g. `assign("a", reg("b"))`. |
| `dataPaths(registers, lines)` | The registers, operations, buttons, entry-point registers and saved registers a controller uses: the analysis of exercise 5.11, and what the Book draws as a machine's data paths. |
| `recordMachine(machine)` | Records every run of a machine as JSON: the code, the data paths, and for each instruction the registers it wrote and what it did to the stack. |
| `parseComponent(text)`, `unparse(component)` | Program text to the tagged-list representation of §4.1.2, which `parse` returns in Source, and back to one line of text. |
| `runEceval(inputs)`, `runCompiled(program, inputs)`, `compileProgram(text)` | The explicit-control evaluator of §5.4 and the compiler of §5.5, both Source programs, run from TypeScript, with the stack statistics of every input. |
| `memoryImage(source)`, `collectGarbage(image)` | A program's pairs as the vectors of typed pointers of §5.3.1, and the stop-and-copy collector of §5.3.2 run on them step by step. |

In Source, `make_machine(register_names, operations, controller)` returns a machine as the message-passing object of §5.2.1, so `start`, `get_register_contents` and `set_register_contents` work as in the book. Besides `"print_statistics"`, a machine's stack answers `"statistics"` with `list(total_pushes, maximum_depth)`, which exercise checks read. `prompt()` and the evaluator's `user_read` return the strings queued by `set_inputs(list(...))`, and `null` when there are none. Operations may be primitives or Source functions; a Source function is applied on a machine of its own.
## Threads

`concurrent_execute(f, g, ...)` gives each function of no arguments a thread of its own: a separate stack of continuations, with the frames shared. After every step a scheduler may switch to another runnable thread, so an assignment such as `balance = balance - amount`, which takes several steps, can be interrupted between reading `balance` and writing it. The call returns `undefined` once all of its threads have finished. `test_and_set(cell)` is a single primitive step, which is what makes it atomic. The scheduler draws from a seeded generator: a `seed` option, accepted by `prepare`, `evaluate` and the `run`, `trace` and `check` requests, replays an interleaving exactly, and a run without one interleaves differently each time. Trace records carry the thread they ran in, and `thread` events mark where threads start and end.

## Inspecting

| Export | What it does |
| --- | --- |
| `processShape(source)` | Returns a `ProcessShapeSnapshot`: for each top-level statement that makes calls, the call depth at every call and return, the maximum depth, and whether the process is recursive or iterative. |
| `maxDepth(source)` | The deepest stack of pending calls in a run. |
| `createCallLogTracer(names)` | Hooks that log every call of the named compound functions, with arguments and result as text and the watched call pending below it. Chapter 4's animations watch the Source functions of an evaluator this way, such as `evaluate` and `apply`. |
| `createStepTracer(source)` | Hooks that record a readable log of evaluation steps, each with its frame id, source span, top-level statement index and a structured `event` (`call`, `return`, `result`, `name`, `define`, `thread` or `eval`) from which the Book's animations rebuild trees, frames and call stacks. |

Inspectors attach through `MachineHooks`: `onEval`, `onCall`, `onReturn`, `onResult`, `onDefine`, `onTopLevelStatement`, `onThread`. A hook observes; it cannot change the result.

## Running off the main thread

| Export | What it does |
| --- | --- |
| `createLabHost({ post })` | The worker side. Handles `run`, `trace`, `check`, `machines`, `memory`, `compare`, `compile` and `cancel` requests and posts events. Jobs run in slices so that a cancel can arrive between them. |
| `LabClient` | The page side. `submit(params, onEvent)` returns a handle with `cancel()` and a `finished` promise that resolves with the terminal event. A worker that does not confirm a cancel is replaced. |

A run may ask to `inspect` its process shape or the calls of named functions. Events for a run are `started`, then any number of `display`, `draw` and `shape`, then a `calls` log if one was asked for, then exactly one of `done`, `error`, `budget-exhausted` or `cancelled`.

A `trace` request returns the step log in one `trace-done` event, together with the program's output and everything it drew.

A `machines` request runs a program and returns, in one `machines-done` event, the record of every register machine it made. A `memory` request lays a program's pairs out in memory and collects the garbage; a `compare` request measures a function interpreted by the explicit-control evaluator and compiled; a `compile` request returns the compiler's code for a program, line by line.

A `check` request runs an exercise's hidden tests, each on a fresh run of the submission. A `value` test compares an expression's value with the expected one. A `shape` test compares an answer with the measured kind of process, recursive or iterative. A `calls` test applies a function and bounds how many times a named function is applied along the way, which is how a check tells a logarithmic process from a linear one that computes the same values. An `error` test passes when a call stops with an error, optionally one whose message contains given text, which is how a check confirms that a program refuses bad input. An `output` test compares what a call displays, line by line, by count, or by text the lines must contain. A check may give a `context`, which is how an exercise replaces a few functions of the simulator or compiler of chapter 5 and runs the rest around them.
