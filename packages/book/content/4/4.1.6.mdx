<Prose>

In JavaScript the scope of a declaration is the whole block that immediately surrounds it, not just the part of the block after the declaration. This section looks more closely at that choice.

Recall the mutually recursive `is_even` and `is_odd` of §3.2.4, declared inside a function `f`. The name `is_odd` in the body of `is_even` must refer to the `is_odd` declared after it; and since `is_odd` in turn refers to `is_even`, the only satisfactory reading is that both names are added to the environment at once. In block structure, a local name’s scope is the entire block in which it is declared.

The evaluator of §4.1.1 achieves this simultaneous scope by scanning out the declarations of a block and extending the environment with a frame for all of them before evaluating any. By the time `is_even` is applied, its environment already binds `is_odd`.

</Prose>

<Example index={0} file="mutual_recursion.sicp" source={mutualRecursionProgram} prelude={metacircularPrelude} budget={5000000}>

Both function declarations are evaluated before `is_even(7)` is: the frame scanned out for `f`’s body binds both names from the start, so each finds the other. Seven is odd, and the value is `false`.

</Example>

## Sequential declaration processing

Scanning out costs time on every evaluation of a block. Alternatively, a block could start with an empty frame, and each declaration could add its binding as it is evaluated:

```js
function eval_block(component, env) {
    const body = block_body(component);
    return evaluate(body, extend_environment(null, null, env));
}
function eval_declaration(component, env) {
    add_binding_to_frame(
        declaration_symbol(component),
        evaluate(declaration_value_expression(component), env),
        first_frame(env));
    return undefined;
}
function add_binding_to_frame(symbol, value, frame) {
    set_head(frame, pair(symbol, head(frame)));
    set_tail(frame, pair(value, tail(frame)));
}
```

Now a declaration’s scope is only the part of the block that follows it. `f` above still works, but for an accidental reason: its internal declarations come first, so neither function is applied before both exist. Sequential processing gives the same results as scanning out whenever the declarations come first in a body and their value expressions do not use the declared names. It is cheaper and simpler, but which declaration a name refers to may then depend on the order in which statements are evaluated. Not everyone agrees whether that is acceptable. ## Recursion without declarations

Recursive functions are obtained in our interpreter in a roundabout way: declare the name, bound to `"*unassigned*"`; make the function in the scope of the name; then assign the function to the name. Amazingly, recursion is possible with neither declarations nor assignment. This expression computes 10 factorial by applying a recursive function to itself:

</Prose>

<Example index={3} file="self_application.sicp" source={selfApplicationProgram}>

`fact` receives itself as its first argument, `ft`, so it can call itself without having a name in any environment. The most general trick of this kind is the *Y operator*, which gives recursion in the pure λ-calculus. Exercise 4.18 asks for Fibonacci numbers in the same style.

<Exercise id="4.16">

Draw a diagram of the environment in effect during the evaluation of the return expression of `f_3` from §1.3.2, which declares `a` and `b` in its body. When a function is applied, the evaluator makes two frames: one for the parameters and one for the names declared directly in the body block. Since all these names have the same scope, the two frames could be one. Change the evaluator so that evaluating a function’s body block does not create a new frame. (You may assume that this does not produce duplicate names in the frame; exercise 4.5 justifies the assumption.)

<Solution>

**Solution.** `apply` scans out the declarations of the body block itself, binds them to `"*unassigned*"` in the same frame as the parameters, and evaluates the block’s body there instead of the block. A body that is not a block, from a lambda expression with an expression body, needs no scanning.

</Solution>
</Exercise>
<Exercise id="4.17">

Eva writes programs in which function declarations and other statements are interleaved, and must make sure that the declarations are evaluated before the functions are applied. Why can’t the evaluator hoist all function declarations to the beginning of the block in which they appear, and those outside blocks to the beginning of the program? Modify the evaluator to do so. JavaScript’s designers took Eva’s approach, and also allowed the name declared by a function declaration to be reassigned. Discuss these decisions.

<Solution>

**Solution.** Every block body and every program reaches `evaluate` as a sequence, so one change suffices: reorder the statements of a sequence so that its function declarations come first. A function declaration has no effects besides binding its name to a function, so evaluating it early changes nothing else; that makes hoisting safe, and convenient. Making the name reassignable, on the other hand, means a call may not reach the function its reader sees declared.

</Solution>
</Exercise>
