<Prose>

One way to see what a program means is as the description of an abstract machine, perhaps an infinitely large one. The familiar factorial

```js
function factorial(n) {
    return n === 1
           ? 1
           : factorial(n - 1) * n;
}
```

describes a machine with parts that decrement, multiply and test for equality, a two-position switch, and another factorial machine inside it. The machine is infinite because it contains a copy of itself.

In the same way, the evaluator is a very special machine. Its input is the description of some other machine, and given that description it configures itself to emulate the machine described. Fed the declaration of `factorial`, it computes factorials.

</Prose>

<Prose>

Seen this way, the evaluator is a *universal machine*: it mimics any other machine that is described as a JavaScript program. Imagine the analogue for electrical circuits, a circuit that takes as input a signal encoding the plans of another circuit, a filter say, and then behaves like that filter. Such a circuit would be almost unimaginably complex. It is remarkable that the program evaluator is a rather simple program.

That JavaScript is the language of the descriptions is inessential. Given a JavaScript program that is an evaluator for C, our evaluator emulates the C evaluator, which can emulate any machine described in C. Any evaluator can emulate any other. What can be computed in principle, ignoring time and memory, is therefore independent of language and computer; it reflects an underlying notion of *computability*, first made clear by Alan Turing in 1936. Turing described a simple model, now called a *Turing machine*, argued that any effective process can be formulated as a program for one (the *Church–Turing thesis*), built a universal machine, and used it to show that there are well-posed problems that no such machine can solve.

The evaluator is also a bridge between the data objects a program manipulates and the programming language itself. To someone typing programs into it, `x * x;` is a program to be executed. To the evaluator it is a string, and after parsing a list, to be manipulated by well-defined rules. The user’s programs are the evaluator’s data, and nothing stops us from building programs as data directly:

<Exercise id="4.15">

Given a one-argument function `f` and an object `a`, `f` is said to *halt* on `a` if evaluating `f(a)` returns a value (as opposed to terminating with an error message or running forever). Show that it is impossible to write a function `halts` that correctly determines whether `f` halts on `a` for any function `f` and object `a`. Use the following reasoning: if you had such a function `halts`, you could implement the following program:

```js
function run_forever() { return run_forever(); }

function strange(f) {
    return halts(f, f)
           ? run_forever()
           : "halted";
}
```

Now consider evaluating `strange(strange)` and show that any possible outcome, either halting or running forever, violates the intended behavior of `halts`. The checker asks what `strange(strange)` does for each answer `halts` could give.

<Solution>

**Solution.** If `halts(strange, strange)` is true, `strange(strange)` runs forever, so `halts` was wrong. If it is false, `strange(strange)` returns `"halted"`, so `halts` was wrong again. Either way `halts` fails on this one input, so no such function exists. This is Turing’s *Halting Theorem*, the first clear example of a *noncomputable* problem; the argument holds even if `halts` may read the function’s text and environment.

</Solution>
</Exercise>
